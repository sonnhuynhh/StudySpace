## 3. TECHNICAL ARCHITECTURE & PROJECT STRUCTURE

### System architecture

```text
iPhone / Expo Go ── Expo Tunnel ── Metro (downloads the app bundle)
       │
       └── HTTPS ── Supabase Auth + Data API ── PostgreSQL
                                                ├── RLS policies
                                                └── transactional RPCs
```

Expo Tunnel distributes the development bundle only. The running app connects directly to Supabase over HTTPS and does not depend on a fixed computer IP or tunnel URL for backend data.

### Authentication flow

Signup calls Supabase Auth with a callback URI generated by `Linking.createURL('auth/callback')`. The app shows an email-waiting state and offers a resend action. When the email link returns to the app, `AuthProvider` handles both initial-launch and in-app links, exchanges the PKCE code or verifies an OTP token, captures the confirmed email, clears the temporary local session and returns to login with the email prefilled.

Expo scheme: `studyspace`. Supabase **Authentication → URL Configuration → Redirect URLs** allows `studyspace://auth/callback` and `exp://**/--/auth/callback` for the corresponding app/Expo Go flows. The Expo Go host changes between sessions; use the wildcard for development and a stable exact redirect in production.

### Database and data flow

- `auth.users` is the authoritative user identity; a database trigger creates the associated `profiles` row.
- `rooms` stores room details; `blocked_slots` stores unavailable periods.
- `bookings` stores owner, room, time range, state and cancellation time.
- RLS scopes profiles and bookings by `auth.uid()`. The app uses a publishable key and user JWT; no service-role secret is bundled.
- Booking operations use PostgreSQL RPCs. Creation rechecks the user, time rules and conflicts in a transaction with a room/date lock. Cancellation retains history; deletion is restricted to the caller's cancelled booking.

### State management and exception handling

TanStack Query caches room, availability and booking data and refreshes related queries after mutations. AsyncStorage persists the Supabase Auth session. Zustand stores search filters, not booking records. Query failures can be retried; cached availability is never treated as proof that a booking write succeeded.

## 5. TECHNICAL CHALLENGES & RESOLUTIONS

### Challenge 1: Expo delivery and backend access use separate connections
- **Issue:** Expo tunnel links change between sessions and are not stable backend addresses.
- **Resolution:** Use the tunnel only to deliver the Metro bundle; call Supabase directly over HTTPS for Auth and data.

### Challenge 2: Returning from email confirmation to Expo Go
- **Issue:** Expo Go uses a dynamic host, and Supabase rejects callback destinations that are not in its redirect allow-list.
- **Resolution:** Generate callback URLs with Expo Linking, configure the `studyspace` scheme, handle cold-start and in-app links, and allow the development patterns in Supabase. Production should use a stable exact redirect.

### Challenge 3: Preventing confirmation from becoming an unexpected login
- **Issue:** Email verification can create a temporary Auth session that may otherwise open protected app screens.
- **Resolution:** Hold routing during callback processing, capture the confirmed email, clear the local confirmation session, display success and return to login with the email prefilled.

### Challenge 4: Concurrent booking attempts
- **Issue:** Multiple devices may see the same time slot as available before a booking is written.
- **Resolution:** PostgreSQL RPCs revalidate ownership and conflicts inside a transaction with a room/date lock; the database result determines whether the booking succeeds.
