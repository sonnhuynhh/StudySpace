## 3. TECHNICAL ARCHITECTURE & PROJECT STRUCTURE

### System architecture

```text
iPhone / Expo Go ── Expo Tunnel ── Metro (downloads app bundle)
       │
       └── HTTPS ── Supabase Auth + Data API ── PostgreSQL
                                                ├── RLS policies
                                                └── transactional RPCs
```

Expo Tunnel only delivers the development bundle. The running app connects directly to the Supabase project over HTTPS; the backend data path does not depend on the computer's LAN IP or a fixed tunnel URL.

### Authentication and email callback

Signup calls Supabase Auth with `emailRedirectTo` generated by `Linking.createURL('auth/callback')`. The app displays a confirmation-waiting view and provides a resend action. On return from the email, `AuthProvider` handles a cold-start or warm deep link, exchanges the PKCE code or verifies an OTP token, obtains the confirmed email, clears the local confirmation session and displays a success state. The UI then returns to login with the email prefilled.

Expo scheme: `studyspace`. Supabase **Authentication → URL Configuration → Redirect URLs** must allow `studyspace://auth/callback` and `exp://**/--/auth/callback` for the corresponding build/Expo Go flows. The Expo Go host is dynamic; use the wildcard only for development and use a stable, exact redirect for production.

### Database and data flow

- `auth.users` is the source of account identity; a database trigger creates the matching `profiles` row.
- `rooms` stores room metadata; `blocked_slots` stores externally unavailable times.
- `bookings` stores the room, owner, time range, status and cancellation time.
- RLS scopes profiles and bookings to `auth.uid()`. The client uses a publishable key and user JWT; it does not contain a service-role secret.
- Booking mutations go through PostgreSQL RPCs. Creation rechecks ownership, schedule rules and conflicts in a transaction with a room/date lock; cancellation retains history; deletion only removes the caller's cancelled booking.

### State and error handling

TanStack Query caches room, availability and booking data and refreshes related queries after mutations. AsyncStorage persists Supabase Auth session. Zustand persists search filters, not booking records. Query errors can be retried; a cached availability display is not treated as a successful booking until the database mutation completes.

## 5. TECHNICAL CHALLENGES & RESOLUTIONS

### Challenge 1: Separating Expo delivery from backend connectivity
- **Issue:** The Expo tunnel URL changes between development sessions and is not a stable API address.
- **Resolution:** Use Expo Tunnel only for Metro bundle delivery and connect the app directly to Supabase through HTTPS. The app does not use a hard-coded LAN IP for backend calls.

### Challenge 2: Returning from email confirmation to Expo Go
- **Issue:** Expo Go creates a dynamic host URL, and Supabase rejects redirect destinations that are not on its allow-list.
- **Resolution:** Build the callback URL dynamically with Expo Linking, register the `studyspace` scheme, process both initial and in-app callback links, and document the development allow-list patterns in Supabase setup instructions.

### Challenge 3: Avoiding unintended sign-in after confirmation
- **Issue:** Verifying an email can create an Auth session, which could otherwise route directly into the protected app.
- **Resolution:** Hold app routing during callback handling, read the confirmed email, clear the temporary local session, show confirmation success, and return to the login form with the email prefilled.

### Challenge 4: Concurrent booking requests
- **Issue:** Two devices may display the same slot as available before either request is saved.
- **Resolution:** PostgreSQL RPCs revalidate the slot inside a transaction and serialize conflicting room/date writes. The server result, not client cache, determines whether the booking succeeds.
